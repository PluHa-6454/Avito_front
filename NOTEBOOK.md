# NOTEBOOK — AI-buddy frontend

> Журнал хода работ по фронтенду AI-buddy. Ведётся по этапам плана `PLAN.md`.
> Здесь фиксируются: что сделано, чем проверено, какие проблемы возникли, как решены,
> какие решения приняты и что осталось.

## Правила ведения

1. Запись после каждого этапа и после каждой значимой проблемы.
2. Формат записи:
   - дата и этап;
   - что сделано;
   - проверки (команды, результат);
   - проблема: симптом → причина → решение → профилактика;
   - отклонения от плана и открытые вопросы;
   - следующий шаг.
3. Фиксировать версии, команды, цифры покрытия, ссылки на файлы/PR.
4. Не скрывать неудачные попытки: они помогают не повторять ошибки.
5. Секреты и реальные ПДн в журнал не попадают.

**Проблемы и решения**

1. **PDF не читается моделью напрямую.**
   - Симптом: инструмент чтения PDF сообщил, что модель не поддерживает PDF.
   - Причина: ограничение модели/инструмента.
   - Решение: извлечение текста через Python (`pymupdf`).
   - Профилактика: для PDF использовать локальный экстрактор, а не пытаться читать файл как изображение.

2. **`pdftotext` потерял кириллицу.**
   - Симптом: в извлечённом тексте остались латиница/цифры, кириллица превратилась в `?`/`�`.
   - Причина: PDF использует Type0/Identity-H шрифты без корректного ToUnicode; консольная
     кодировка дополнительно искажает вывод.
   - Решение: `pymupdf` + `page.get_text("rawdict")`; символы извлекаются по коду, а не по
     отображению в консоли; текст сохранён в UTF-8 и прочитан корректно.
   - Профилактика: проверять извлечённый текст на наличие кириллицы; для сложных PDF использовать
     `rawdict`, при необходимости — OCR.
   - Временные файлы анализа удалены; репозиторий оставлен без изменений.

3. **В ТЗ нет готового OpenAPI, а бэкенд ещё не написан.**
   - Симптом: фронту не на что опереться, кроме §10 ТЗ; часть деталей не определена.
   - Причина: бэкенд разрабатывается после фронта.
   - Решение: contract-first — `api/openapi.yaml` + Zod-схемы + mock-сервер; спорные места
     помечены как contract proposals (идемпотентность сообщения, формат confirm/409, история действия,
     тело логина, `/mentor`).
   - Профилактика: любые изменения контракта — через `docs/frontend/contracts.md`, схемы, mock и тесты;
     после появления бэкенда — сверка и contract tests.

4. **`/mentor` (P2) не имеет контракта.**

  шаг онбординга закрыт → `429` с `Retry-After: 30`.

**Проблемы и решения**

1. **SSE-ответ зависал после первого шага.**
   - Симптом: `POST /messages` не завершался, клиент ждал до таймаута.
   - Причина: `req.on('close')` в Express 5 срабатывает после чтения тела запроса, а не при
     отключении клиента; флаг `clientClosed` сразу становился `true`, и `res.end()` не вызывался.
   - Решение: слушать `res.on('close')` и проверять `res.writableEnded`; завершать ответ всегда,
     если он ещё не завершён.
   - Профилактика: для SSE проверять отключение по `res`, а не по `req`.

2. **На порту 4010 остался старый минимальный mock.**
   - Симптом: login возвращал HTML вместо JSON.
   - Причина: процесс с прошлой проверки `healthz` не был остановлен и слушал порт; новый сервер
     не мог занять порт.
   - Решение: процесс остановлен по PID, сервер перезапущен.
   - Профилактика: перед запуском проверять `netstat -ano | findstr :4010`; в E2E использовать
     отдельный порт.

3. **AbortError в jsdom не является `DOMException`.**
   - Симптом: тест таймаута получал `NETWORK` вместо `TIMEOUT`.
   - Причина: `fetch`/undici в jsdom отклоняет промис обычной ошибкой с `name: 'AbortError'`.
   - Решение: проверять и `DOMException`, и `error.name`.
   - Профилактика: не завязываться на класс ошибки, только на `name`.

4. **Типы Express 5 и MSW 3.**
   - Симптом: `req.params.*` имеет тип `string | string[]`; `HttpResponse` требует generic;
     `server.listen({onUnhandledRequest})` не проходит по типам.
   - Решение: `String(...)` для параметров, вывод типа `HttpResponse` без аннотации,
     `server.listen()` без опций.
   - Профилактика: проверять типы после обновления major-версий.

**Отклонения от плана**
- Для lint используется `oxlint` (Vite 8 scaffold), а не ESLint + jsx-a11y. Отклонение
  зафиксировано на этапе 1; a11y-проверки вынесены в этап 3/9.

**Проблемы и решения**

1. **Ленивые маршруты сломали синхронные тесты.**
   - Симптом: 8 падений, в DOM — скелетон «Загружаем страницу».
   - Причина: `getBy*` не ждёт Suspense, а холодный импорт дольше 1 с.
   - Решение: прогреваем страницы в `src/test/setup.ts`, переводим синхронные проверки на
     `findBy*`, поднимаем `asyncUtilTimeout` до 3 с.
   - Профилактика: для lazy-маршрутов в тестах всегда использовать асинхронные запросы.

2. **Один тест упал только под покрытием.**
   - Причина: гонка таймаута при инструментировании и холодном импорте.
   - Решение: увеличенный `asyncUtilTimeout` + повторный прогон; нестабильность не воспроизвелась.
   - Профилактика: следить за временем выполнения тестов в CI и держать запас таймаута.

3. **Предупреждение о размере чанка.**
   - Причина: `react-markdown`, Radix и все страницы в одном бандле.
   - Решение: route-level `React.lazy`.
   - Профилактика: тяжёлые визуальные зависимости держать в чанке своей страницы.
