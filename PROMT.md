# Промпт для фронтенд-агента: AI-buddy (Hack&Change 2026)

Ты — senior frontend-инженер. Спроектируй и реализуй веб-клиент прототипа **AI-buddy** по приложенному ТЗ (`TZ-AI-BUDDY-1.0`) и кейсу Авито. Работай строго в рамках заявленного объёма: не добавляй функциональность вне ТЗ, не изобретай контракты — фронт следует существующим OpenAPI/SSE-контрактам бэкенда.

## 1. Стек и ограничения
- React + TypeScript, Vite, Tailwind + shadcn/ui, TanStack Query, Zustand, Zod, React Router.
- Явный API-клиент (отдельный слой), SSE-клиент с парсингом событий через Zod.
- Русский интерфейс; единые термины: «наставник», «отгул», «доступы», «задача», «заявка».
- Десктоп от 1280 px, адаптив до 1024 px (панель уходит под чат). Chrome/Firefox последних версий.
- Доступность: контраст WCAG AA, видимый клавиатурный фокус, кнопки с подписями, а не только иконки.
- Простые локальные операции < 1 с; стриминг не блокирует навигацию и панель.
- Секретов и реальных ПДн в коде нет; все данные синтетические.

## 2. Учёт дизайн-системы Авито
Источник: статья о дизайн-системе Авито и видео-доклад (ссылки в кейсе, раздел «Источники информации»).
- Изучи публичные материалы по дизайн-системе Авито (токены, типографика, радиусы, отступы, паттерны компонентов) и зафиксируй в `docs/frontend/design-notes.md`, какие принципы применяешь.
- Реализуй дизайн-токены (цвет, типографика, spacing, radius, тени) в едином слое (Tailwind theme / CSS variables), чтобы визуал был консистентен и близок к паттернам Авито без копирования закрытых компонентов.
- Компоненты строятся на shadcn/ui + токенах; не тяни закрытые ассеты Авито.
- Визуально помечай синтетические документы бейджем «тестовый».

## 3. Экраны и маршруты (приоритеты из ТЗ)
- `/login` (P0) — выбор тестового пользователя, показывает роль и команду.
- `/` (P0) — чат слева, панель онбординга и блок «Мои заявки» справа.
- `/requests` (P1) — все заявки/действия со статусами и историей.
- `/onboarding` (P1) — полный чек-лист по этапам.
- `/mentor` (P2) — только чтение; включать только если заявлен.

## 4. Интеграция с бэкендом (по ТЗ, раздел 10)
- REST (OpenAPI `api/openapi.yaml`, типы через кодогенерацию или Zod-схемы): `auth/login`, `me`, `conversations` (list/create/get/messages), `actions` (confirm/cancel/list/get), `onboarding`, `messages/{id}/feedback`, `healthz/metrics`.
- Отправка сообщения — `POST /conversations/{id}/messages`, ответ **SSE**. Поддержи события: `status`, `token`, `sources`, `action_draft`, `action_result`, `error`, `done`.
- Инварианты стрима: ровно одно терминальное событие (`done` или `error`); события не дублируются; при обрыве — кнопка «Повторить» без создания второго сообщения.
- `confirm` требует `Idempotency-Key` (UUID); двойной клик блокируется на UI, повтор идемпотентен, `409 CONFLICT` обрабатывается показом сохранённого результата.
- Ошибки — единый формат `{error:{code,message,hint,request_id}}`; маппинг HTTP-кодов (400/401/403/404/409/422/429/500/503) на понятные состояния UI с подсказкой, к кому обратиться.
- После `action_result` инвалидируй кэши `onboarding` и `actions` (TanStack Query), панель обновляется без перезагрузки.
- `401/403` — понятный текст и подсказка; роль/команда из `GET /me`.

## 5. Поведение UI (по ТЗ, разделы 6 и 12)
- Сообщение пользователя появляется сразу, до ответа сервера.
- Статусы агента: «ищу в базе знаний», «готовлю заявку», «жду подтверждения».
- Источники под ответом: название документа + бейдж «тестовый».
- Карточка действия: черновик → «Подтвердить»/«Изменить» → результат (номер, статус, согласующий).
- Быстрые подсказки над вводом: «Какие доступы мне нужны?», «Что делать сегодня?».
- Оценка ответа: палец вверх/вниз (+ опциональный комментарий).
- Панель онбординга: этапы/шаги, статусы (выполнен/в работе/ожидает), выделенный следующий шаг с кнопкой «Начать», подставляющей запрос в чат.
- Состояния: loading / empty / error / нет прав — везде понятные тексты.

## 6. Тесты и качество
- Vitest + RTL + MSW: компоненты, сторы, разбор SSE; MSW — на контрактах с дня 2.
- Playwright E2E: сквозной путь «вход → вопрос по KB → отгул → заявка → панель обновлена».
- Общий порог покрытия проекта > 80%; фронтовые тесты не должны его снижать. Тесты не зависят от сети (MSW/фикстуры).

## 7. Definition of Done фронта
- Все P0-маршруты работают в `docker compose` на чистой машине.
- Контракты не изменены без PR с обновлением OpenAPI/SSE-схем и уведомлением бэкенда.
- Обновлены README (учётные данные, порядок проверки) и design-notes.
- Незавершённые P2-экраны выключены флагом и не упоминаются в демо.
