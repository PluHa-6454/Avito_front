# PLAN — AI-buddy, фронтенд (Hack&Change 2026)

> Рабочий план разработки веб-клиента AI-buddy по ТЗ `TZ-AI-BUDDY-1.0` и кейсу Авито.
> Бэкенд на старте отсутствует. Фронтенд разрабатывается contract-first: мы фиксируем REST/SSE-контракт,
> реализуем его в mock-слое и пишем клиент так, чтобы позже заменить mock на реальный `buddy-api` без
> переписывания UI. После завершения фронта по этому же контракту пишется бэкенд.

---

## 0. Принятые решения и допущения

| № | Решение | Обоснование |
|---|---------|-------------|
| 1 | Фронтенд живёт в `web/`, корень репозитория — монорепо по Приложению A ТЗ | Позже рядом появятся `cmd/`, `internal/`, `api/`, `deploy/`; фронт не смешивается с бэкендом |
| 2 | Контракт — `api/openapi.yaml` + Zod-схемы в `web/src/shared/api/schemas` | Бэкенда и готового OpenAPI нет; ТЗ §10 формализуем в контракт, который станет заданием для бэкенда |
| 3 | Источник истины по типам — Zod; TS-типы выводятся из схем | Один слой валидации рантайма и типов, меньше расхождений |
| 4 | Для разработки и E2E — отдельный mock-сервер (Express + SSE), для юнит-тестов — MSW | MSW удобен для REST в тестах; реальный SSE надёжнее проверять на настоящем HTTP-сервере |
| 5 | Стриминг живёт в singleton `StreamManager` вне React-дерева | Навигация и панель не блокируются, стрим не обрывается при переходе между экранами |
| 6 | Токен хранится в `sessionStorage` (прототип) | В production нужен httpOnly/Secure cookie; для синтетического JWT прототипа достаточно, риск фиксируем в docs |
| 7 | `/mentor` — P2, по умолчанию выключен флагом и не регистрируется в роутере | Контракт P0/P1 берём из ТЗ §10; для `/mentor` в ТЗ есть только экран и tool `mentor.ask`, но нет REST-эндпоинтов прогресса/обращений. **Подтверждено 2026-11-13: P2 off, контракт mentor — backlog.** |
| 8 | «Изменить» в карточке действия = отменить черновик и подставить текст в чат | В контракте нет PATCH действия; изменение делается новым запросом к агенту, без выдуманных эндпоинтов |
| 9 | P0 → P1 → P2, при конфликте сроков P2 снимается первым | Соответствует ТЗ §3.5 и правилу «всё или ничего» |
| 10 | Все данные синтетические; документы и источники помечаются «тестовый» | Требование ТЗ и кейса |

### Открытые контрактные вопросы (решаются на этапе 0–2)

Это не блокеры для старта, но их нужно зафиксировать в `docs/frontend/contracts.md` и согласовать с будущим бэкендом:

1. **Идемпотентность отправки сообщения.** Чтобы «Повторить» после обрыва SSE не создавало второе сообщение,
   предлагаем в `POST /conversations/{id}/messages` передавать `client_message_id` (UUID) и сделать создание
   пользовательского сообщения идемпотентным. Если бэкенд не примет — обсудить альтернативу (заголовок
   `Idempotency-Key` на отправку сообщения).
2. **Ответ `confirm`.** Предлагаем `POST /actions/{id}/confirm` → `200 {action: Action}` с результатом.
   Событие `action_result` в SSE поддерживаем, но не считаем единственным каналом результата.
3. **Формат `409 CONFLICT`.** Предлагаем `{error: {...}, action?: Action}`; фронт умеет и это, и fallback
   `GET /actions/{id}`.
4. **История действия.** Для `/requests` нужна история статусов; предлагаем `Action.history: ActionEvent[]`
   в `GET /actions/{id}`.
5. **Тело логина.** Для тестовых пользователей предлагаем `POST /auth/login {email}` без пароля.
6. **`/mentor`.** В ТЗ §10 нет REST-эндпоинтов для прогресса стажёров и переданных вопросов; есть только экран и tool `mentor.ask`. Пока P2 off. Если включаем — сначала добавляем в контракт `GET /mentor/mentees`, `GET /mentor/requests` и т.п. как proposal, затем UI и тесты.

## 2. Архитектура фронтенда

### Слои

```
┌─────────────────────────────────────────────────────────────┐
│ pages / features (UI, сценарии, компоненты)                 │
├─────────────────────────────────────────────────────────────┤
│ hooks + Zustand stores + TanStack Query                     │
│  authStore · chatStore/streamStore · query keys             │
├─────────────────────────────────────────────────────────────┤
│ StreamManager (singleton, вне React)                        │
│  fetch POST → ReadableStream → SSE parser → события в store │
├─────────────────────────────────────────────────────────────┤
│ API-клиент (явный слой)                                     │
│  apiFetch<T> · endpoints · ошибки · Zod-валидация           │
├─────────────────────────────────────────────────────────────┤
│ Контракт: Zod-схемы + api/openapi.yaml + SSE-схемы          │
└─────────────────────────────────────────────────────────────┘
              │ dev/test                         │ prod
              ▼                                  ▼
      mock-сервер (Express+SSE)          buddy-api (позже)
      MSW (юнит-тесты)
```

### Ключевые технические решения

- **Стек:** React 19 + TypeScript (strict), Vite, Tailwind CSS + shadcn/ui, TanStack Query v5,
  Zustand, Zod, React Router. Версии фиксируются в `package.json`/lockfile на этапе 1.
- **API-клиент:** `fetch` + обёртка `apiFetch`, Bearer-токен, таймаут, нормализация ошибок,
  Zod-валидация успешных ответов и ошибок. 401 → глобальное событие выхода; 403 → состояние «нет прав»;
  409 → показать сохранённый результат.
- **SSE:** `fetch` + `ReadableStream` (не `EventSource`, потому что POST и нужен `Authorization`).
  Парсер — конечный автомат: буфер, границы `\n\n`/`\r\n\r\n`, многострочный `data`, комментарии,
  неизвестные события игнорируются, после терминального (`done`/`error`) события не применяются.
- **StreamManager:** один активный стрим на диалог; `AbortController`; запись в Zustand; батчинг токенов
  (rAF/50 мс) для производительности; при завершении — инвалидация сообщений/диалогов/онбординга/заявок.
- **Идемпотентность:** `crypto.randomUUID()`; ключ создаётся один раз на попытку подтверждения и
  переиспользуется при ретраях; кнопка блокируется синхронно (`isPending` + ref-guard).
- **Кэши:** TanStack Query; ключи `['me']`, `['conversations']`, `['messages', id]`, `['actions']`,
  `['action', id]`, `['onboarding']`; после `action_result`/успешного confirm — инвалидация
  `['onboarding']` и `['actions']` (плюс `['action', id]`).
- **Роутинг:** `/login`, `/`, `/requests`, `/onboarding`, `/mentor` (флаг), `*`. Выбранный диалог — в
  query-параметре `?conversation=id`, чтобы работали reload и deep link.
- **Доступность:** семантические лендмарки, видимый фокус, подписи у кнопок, `aria-live` для статусов
  (не на каждый токен), контраст WCAG AA, поддержка `prefers-reduced-motion`.

### Поток отправки сообщения

1. Пользователь вводит текст → сообщение сразу появляется в UI (optimistic, временный id).
2. Если диалога нет — `POST /conversations`, затем `POST /conversations/{id}/messages`.
3. StreamManager открывает SSE, события `status/token/sources/action_draft/action_result/error/done`
   пишутся в `streamStore`; UI обновляется.
4. `done` → сообщение фиксируется, инвалидация истории; `error`/обрыв → сообщение с ошибкой и «Повторить».
5. «Повторить» переиспользует `client_message_id`, не создаёт второе сообщение.

### Поток подтверждения действия

1. `action_draft` → карточка `draft` с кнопками «Подтвердить», «Изменить», «Отменить».
2. «Подтвердить» → ключ UUID, кнопка блокируется, `POST /actions/{id}/confirm`.
3. Успех → карточка `done` с номером/статусом/согласующим; инвалидация `onboarding` и `actions`.
4. `409` → показать сохранённый результат (из тела или `GET /actions/{id}`), без дубля.
5. `403/422/429/5xx` → понятное состояние в карточке, ретрай только там, где он безопасен.
6. «Изменить» → `cancel` черновика + подстановка текста в чат; «Отменить» → `cancel`.

## 3. Контракт (бэкенда нет)

### Что фиксируем

- `api/openapi.yaml` — REST: auth, me, conversations, messages, actions, onboarding, feedback, healthz/metrics.
- `web/src/shared/api/schemas/*.ts` — Zod-схемы и выведенные типы.
- `web/src/shared/api/sse.ts` — Zod-схемы событий SSE.
- `docs/frontend/contracts.md` — человекочитаемое описание, примеры, инварианты, открытые вопросы.

### События SSE

| Событие | Payload | Поведение UI |
|---------|---------|--------------|
| `status` | `{stage, text}` | строка статуса агента |
| `token` | `{text}` | дописывание текста ответа (батчинг) |
| `sources` | `{items: [{doc_id,title,synthetic}]}` | список источников, бейдж «тестовый» |
| `action_draft` | `{action_id,type,fields}` | карточка черновика |
| `action_result` | `{action_id,status,result}` | обновление карточки, инвалидация кэшей |
| `error` | `{code,message}` | терминальная ошибка + «Повторить» |
| `done` | `{message_id}` | терминальное успешное завершение |

Инварианты: ровно одно терминальное событие; события после терминального игнорируются; дубли
терминального не применяются; при обрыве без терминального — ошибка соединения и «Повторить».

### Ошибки

Единый формат `{error:{code,message,hint,request_id}}`. Маппинг:
`400` — проверьте данные; `401` — сессия истекла, вход заново; `403` — нет доступа + подсказка,
к кому обратиться; `404` — не найдено; `409` — уже выполнено, показать результат; `422` — действие
недоступно, объяснение; `429` — лимит, повтор через N секунд; `500` — ошибка, request_id, повторить;
`503` — AI временно недоступен, повторить; сеть — нет соединения, повторить.

## 4. Mock-слой (пока нет бэкенда)

### Состав

- `web/mocks/server.ts` — Express-сервер, порт 4010, все REST-эндпоинты + SSE.
- `web/src/mocks/fixtures` — пользователи, KB-документы команд A/B, онбординг, заявки, диалоги.
- `web/src/mocks/scenarios` — сценарии ответов: KB, отгул, доступы, задача, отказ, ошибка LLM,
  медленный стрим, 409, 403, 429, 500/503.
- `web/src/mocks/core` — чистая логика in-memory store (создание диалога, сообщения, действия,
  идемпотентность, онбординг), которую используют и mock-сервер, и MSW-хендлеры.
- `web/src/test/handlers.ts` — MSW для REST в юнит/компонентных тестах.
- `web/src/test/sse.ts` — хелпер `ReadableStream` из массива событий для тестов парсера/хука.

### Демо-сценарии mock-сервера

| Запрос | Сценарий |
|--------|----------|
| «Как у нас устроено код-ревью?» | `status kb_search` → `sources` (команда A, `synthetic: true`) → токены → `done` |
| «Хочу взять отгул в пятницу» | инструкция → `action_draft absence.create` → `done`; confirm → результат с номером/статусом/согласующим |
| «Какие доступы мне нужны?» | разница доступов → `action_draft access.request`; confirm → статус; шаг закрывается |
| «Что делать сегодня?» | список задач → `action_draft tasks.transition`; confirm → «в работе» |
| Вопрос вне базы | честный отказ + предложение `mentor.ask` (черновик) |
| `intern2@` + вопрос по KB команды A | отказ/пустые источники, без документов чужой команды |
| Спец. текст/заголовок для теста | `error LLM_UNAVAILABLE`, обрыв стрима, медленный стрим, 409 |
| Повторный confirm с тем же ключом | тот же результат, без дубля |
| Confirm с другим ключом после done | `409` + сохранённый результат |

Mock-сервер также даёт тестовые `POST /__mock/reset` и `POST /__mock/config` (только для E2E,
не часть продуктового контракта), чтобы тесты были детерминированными.

## 6. Дизайн-система и UI

### Источники и принципы

Изучаем публичные материалы: статью о дизайн-системе Авито (Habr, 543450), видео-доклад, AvitoTech
Playbook. Фиксируем в `docs/frontend/design-notes.md`:

- единый слой стилей: названия токенов в коде совпадают с дизайн-названиями;
- типографика как набор стилей `heading/body/caption` с размером и интерлиньяжем;
- цветовая палитра от светлого к тёмному + семантические токены;
- библиотека компонентов с вариантами и состояниями (default/hover/focus/disabled/loading/error);
- спецификации для разработчиков и гайдлайны; проверка светлой/тёмной темы;
- платформенные различия: на десктопе — поповеры/диалоги, на узком экране — панель под чатом;
- не копируем закрытые ассеты и компоненты Авито; используем shadcn/ui + собственные токены.

### Токены (черновой состав)

- **Цвет:** brand (50–900), neutral (50–900), success, warning, danger, info; семантические
  `background`, `foreground`, `card`, `muted`, `border`, `primary`, `ring`, `destructive`.
  Основной цвет кнопок — достаточно тёмный для контраста AA; декоративный brand — светлее.
- **Типографика:** системный стек с кириллицей (`Inter, -apple-system, "Segoe UI", Roboto, ...`);
  display 28/36, h1 24/32, h2 20/28, h3 16/24, body 14/20, small 13/18, caption 12/16; веса 400/500/600.
- **Spacing:** база 4 px: 4, 8, 12, 16, 20, 24, 32, 40, 48, 64.
- **Radius:** 8 — контролы, 12 — карточки, 16 — модальные окна, full — пилюли.
- **Тени:** мягкие, только для поднятых слоёв; без тяжёлых градиентов.
- **Фокус:** 2 px ring + offset 2; видимый на всех интерактивных элементах.
- **Motion:** 150–200 мс ease-out; `prefers-reduced-motion` отключает анимации.
- **Breakpoints:** 1024, 1280, 1440; десктоп-приоритет, панель уходит под чат < 1024.

### Каркас экранов

- **AppShell:** шапка 64 px (логотип, навигация «Чат / Заявки / Онбординг», чип роли и команды, выход),
  основная область. На < 1024 навигация — горизонтальные вкладки.
- **`/`:** чат слева (гибкая ширина), правая панель 380 px (онбординг + «Мои заявки»); < 1280 — 340 px;
  < 1024 — панель под чатом. Внутри чата: заголовок диалога/селектор, лента сообщений, быстрые подсказки,
  статус агента, композер.
- **`/requests`:** список заявок с фильтрами по статусу/типу, карточки/строки, деталь в drawer с историей.
- **`/onboarding`:** полный чек-лист по этапам, прогресс, следующий шаг, кнопки «Начать».
- **`/login`:** сплит-экран: ценность продукта + карточки четырёх тестовых пользователей.
- **`/mentor`:** не регистрируется при `VITE_FEATURE_MENTOR_PAGE=false`; в навигации отсутствует.

### Компоненты

shadcn/ui: Button, Input, Textarea, Card, Badge, Tabs, Dialog, Sheet, Tooltip, Skeleton, Alert, Avatar,
ScrollArea, Separator, DropdownMenu, Sonner. Кастомные: `AppShell`, `PageHeader`, `MessageBubble`,
`StreamingMessage`, `AgentStatus`, `SourceList`, `SyntheticBadge`, `ActionCard`, `QuickPrompts`,
`FeedbackButtons`, `OnboardingPanel`, `OnboardingStep`, `RequestCard`, `RequestDetail`,
`EmptyState`, `ErrorState`, `NoAccessState`, `RoleChip`.

### Тексты и термины

Только русский UI. Единые термины: «наставник», «отгул», «доступы», «задача», «заявка».
Статусы агента: «Ищу в базе знаний», «Готовлю заявку», «Жду подтверждения» (плюс fallback на текст сервера).
Ошибки — с подсказкой, к кому обратиться; `request_id` показываем в деталях.

## 7. Поэтапный план

> Оценка — ориентир для одного фронтенд-инженера; при работе агента этапы идут последовательно,

## 9. Тестовая стратегия

### Уровни

- **Юнит:** SSE-парсер, API-клиент, нормализация ошибок, idempotency-ключи, сторы, маппинг статусов.
- **Компонентные (RTL):** login, chat, message, sources, action card, onboarding panel, requests,
  states; клавиатура и aria.
- **Интеграционные:** MSW REST + тестовый SSE-стрим; сценарии confirm/409/retry.
- **E2E (Playwright):** сквозной путь, двойной клик, изоляция команд, ошибка/retry, навигация во время
  стрима, адаптив 1280/1024.
- **Доступность:** axe (опционально) + ручная проверка фокуса/контраста/клавиатуры.

### Покрытие

- Провайдер V8, пороги 80% по lines/functions/branches/statements.
- Включаем `src/**/*.{ts,tsx}`; исключаем только сгенерированные shadcn-примитивы, типы,
  mock/fixtures, тестовый setup и `main.tsx` (тривиальный bootstrap).
- Отчёт: `docs/coverage/` + артефакт CI; фиксируем цифры в NOTEBOOK.
- CI не пропускает PR при падении покрытия ниже порога.

### Детерминированность

- Никакой сети в тестах: MSW, фикстуры, fake timers, тестовый SSE-хелпер.
- Mock-сервер для E2E с `POST /__mock/reset` перед каждым тестом; фиксированные задержки/скорость.
- Playwright `workers: 1` на старте; позже — изоляция по пользователям/диалогам.

## 10. Риски и меры

| Риск | Вероятность | Влияние | Мера |
|------|-------------|---------|------|
| Контракт разойдётся с будущим бэкендом | Высокая | Высокое | Zod + OpenAPI + contract tests + mock как эталон; изменения только через PR/док |
| SSE в MSW/браузере нестабилен | Средняя | Среднее | Отдельный mock-сервер для dev/E2E; парсер тестируем независимо; спайк на этапе 2 |
| Нет механизма идемпотентности сообщения | Средняя | Высокое | `client_message_id` как contract proposal; согласовать до бэкенда; иначе retry может дублировать |
| Формат 409/confirm неизвестен | Средняя | Среднее | Гибкий парсер + fallback `GET /actions/{id}`; зафиксировать в contracts.md |
| Стрим тормозит UI | Средняя | Среднее | Батчинг токенов, изолированный компонент стрима, memo, профилирование |
| Потеря стрима при навигации | Средняя | Среднее | StreamManager вне React; тест навигации во время стрима |
| Покрытие < 80% | Средняя | Высокое | Тесты с первого дня, гейт в CI, отчёт ежедневно |
| P2/mentor расползётся по объёму | Средняя | Среднее | Флаг off, route не регистрируется, в демо не упоминается |
| Токен в sessionStorage | Низкая | Среднее | Прототип; зафиксировать в docs, production — httpOnly cookie |
| Windows/пути/Playwright | Средняя | Низкое | Кроссплатформенные скрипты, `cross-env`, lockfile, инструкция в NOTEBOOK |
| Доступность стрима для скринридеров | Средняя | Среднее | `aria-live` только на статусы/завершение, не на каждый токен |
| Даты/часовые пояса в отгуле | Средняя | Низкое | ISO-даты от API, формат `ru-RU`, без клиентской бизнес-логики |
